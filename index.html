OpenShell — Architectural Decisions

A VS Code–style desktop GUI for the opencode2 agent. This page explains why the system is built the way it is.

01Process model: only the main process talks to opencode2

OpenShell is an Electron app with three build targets (main, preload, renderer). The defining rule is that the Electron main process is the only process that imports @opencode-ai/client and talks to the opencode2 service.

Electron MAIN  — window, IPC, OpenShellBackend (all opencode2 traffic)
     │  ipcRenderer.invoke()  (renderer → main, request/response)
     │  webContents.send()    (main → renderer, push events)
     ▼
PRELOAD (contextBridge)  →  window.openshell API
     ▼
RENDERER (React 19 + Monaco) — store.tsx holds all UI state

Why: the opencode2 client API and event shapes are beta and shift frequently. Isolating every API call in src/main/opencode.ts means a client-version bump touches exactly one file. The renderer never sees the client, and the main process never ships library code to the UI.

02Renderer isolation: contextIsolation + no Node in the UI

The BrowserWindow runs with contextIsolation: true and nodeIntegration: false. The renderer has zero Node access — no fs, no child_process, no process env. Every capability is explicitly exposed by the preload script as window.openshell methods, and only those.

Why: it is the standard Electron security posture, and it forces a clean API boundary. File I/O, PTY output, and opencode2 traffic are all main-process concerns; the renderer just calls the bridge. There is no path for a compromised renderer (say, a malicious file preview) to reach the filesystem or the service outside the whitelisted surface.

03Shared types as the single contract

src/shared/types.ts is imported by main, preload, and renderer as @shared/types. It defines the wire format between the processes: BackendMessage (a discriminated union on kind), Tab, TranscriptItem, FileUpdate, IPC argument shapes, and so on.

Why: three processes compile against one contract. Change a type in the shared file and both sides of the bridge must adapt — TypeScript won't let either side drift. IPC-shape types live here and nowhere else.

04Two IPC idioms: invoke for calls, one push channel for events

Renderer→main is synchronous request/response over shell:* channels (ipcRenderer.invoke / ipcMain.handle) — e.g. shell:fs-read, shell:prompt, shell:switch-model.

Main→renderer is a single firehose: webContents.send("shell:message", msg). Every backend event — opencode2 SSE events, file watcher updates, session changes, PTY output, UI commands — travels over that one channel as a BackendMessage.

Why: a single push channel keeps the main process emitter plumbing trivial (everything is one onMessage subscription fanning out) and forces every message to be a typed, self-describing envelope. The renderer's store subscribes once and dispatches on kind/type.

05SSE event streaming with automatic reconnection

The backend subscribes to the opencode2 service's SSE stream (client.event.subscribe) and forwards every event verbatim as {kind:"event", type, data}. The renderer decides what matters — handled event types live in docs/events.md, and anything unhandled is deliberately ignored rather than driving UI.

Both connections self-heal: connect() retries every 2s until a client exists, and the SSE loop re-connects with a 1.5s retry on drop. On macOS, closing the window does not tear down the backend — re-activating re-creates the window and calls start(), because the backend is designed to be restartable.

Why: opencode2 is a long-running streaming service and the app must survive service restarts and window churn without losing the session.

06Baselines: what "the diff" means

The center pane shows, per file, exactly what the agent changed this session. The main process derives that from per-file baselines, resolved in priority order:

  1. Tool snapshot — when session.tool.called arrives, files named in the tool input (filePath/file_path/path) are read and stored as their baseline before the tool runs.
  2. git fallback — files first seen via fs.watch get git show HEAD:<rel> as baseline when the repo has a .git.
  3. First-seen — otherwise the first observed content becomes the baseline (so new files diff green against nothing).

Why: the diff must mean "changes the agent made in this session", not "changes since last commit". Tools like bash edit files without a visible file-writing step, so the tool-call snapshot is what makes those diffs correct.

07Writes go through Node fs, not the API

The opencode2 API has no file-write endpoint. So editor saves (shell:fs-write) write through Node fs in the main process; the opencode2 server notices the change through its own file watching. The app keeps its own watcher (fs.watch, recursive, 200ms debounced) to stream file-update messages into the UI.

Autosave is debounced 900ms and also fires on ⌘S. Edits originating in the editor are tracked in an expectedRef so the watcher's own echo doesn't falsely mark a tab dirty/stale.

08Session lifecycle: one session per app run

Opening a folder creates a session via client.session.create({ location: { directory } }) with the last-used model/agent from settings.json. Exactly one session is active per run; a history of recent sessions exists on the Welcome screen and reopening one resumes its context (transcript replayed from message.list).

Why: one active session keeps the baseline map, watcher, and UI state unambiguous. No multi-session complexity is bought until real usage demands it.

09The terminal tray is a real PTY in the main process

The bottom tray runs node-pty in the main process, spawning the login shell (zsh -l on macOS) in the session directory. PTY output flows to the renderer as terminal-data messages; keystrokes go back via shell:terminal-input; resizes use the xterm fit addon.

Why: a real PTY (not a fake terminal) gives correct interactive behavior — line discipline, colored output, signals. node-pty is rebuilt against Electron's ABI via @electron/rebuild, so it's a native-module exception to the otherwise pure-JS main process.

10Persistence: a tiny settings.json

Last-used model (with variant) and agent are persisted to settings.json under Electron's userData path. New sessions start on the same model/agent the user chose last time. Everything else is ephemeral — there's no database.

Why: YAGNI. The only cross-session state worth keeping is the model/agent preference; session history itself comes from the opencode2 service, not the app.

11The docs are the brain — and they're checked

AGENTS.md + docs/ form the project's living specification. The docs are machine-checked: npm run docs:check (via scripts/check-docs.mjs) verifies that the IPC channel table matches src/main/index.ts, the method table matches OpenShellBackend's public methods, the window.openshell contract matches the preload script, and every handled event in docs/events.md has a matching case in the store.

Why: the docs can never silently drift from the code. Any agent editing this repo updates the brain in the same commit as the code that makes the change necessary, and docs:check fails the build on drift.
